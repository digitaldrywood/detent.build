The inversion

You are not steering an agent. You are running your process at scale.

Autonomy-first assistants keep memory, pick their own tools, and ask you to course-correct when they drift. Detent inverts that: you write the issue first — scope, acceptance criteria, tests, dependency order, review policy, merge rule — and the board state decides when it is eligible. The intelligence stays in your spec. The runtime supplies the discipline.

“add OAuth token rotation”, elsewherethe same task, in Detent
A prompt that becomes a supervision loop: review the plan, inspect partial edits, redirect when it misses the migration, redirect again when it skips tests.
An issue that names the storage change, CLI behavior, migration, rollback, and tests. The worker produces a reviewable PR — and does not merge until the gates are green.
How it works

The mechanism, stop by stop.

1
You write the contracts

A checked-in detent.yaml — tracker bindings, states, lifecycle policy, scheduling, retries, leases, gates — plus a portable WORKFLOW.md agent contract. Gitignored *.local overrides keep machine-specific config off the shared files. The lanes themselves are yours to define — these six are just the defaults Detent runs on itself.

2
You mark an issue Todo

Detent claims it, creates an isolated Git worktree from your checkout, dispatches a Codex agent with the contract, and moves the issue to In Progress.

3
The agent works

In its own branch. It runs your validation gate and opens or updates a PR.

4
Gates decide — this is the detent

Promotion to Merging waits in Human Review, waits in the active lane, requires a current-head automated PR review, or only needs linked PR + green CI + quiet time — whichever your workflow specifies. Unresolved feedback sends it to Rework for another pass.

5
The merge train is serialized

One rebase, CI-watch, and merge at a time — the width is config; ours is one — so concurrent candidates never invalidate each other's CI. Then the issue is Done.

6
One host, many repos

A global.yaml runs multiple projects with weights, priority, pause, and fair scheduling. Boards can be GitHub ProjectV2, an issue Status field, or repository labels — Detent supplies its own Kanban view either way.

The merge train

Serialized. Always green.

Serialized rebase → CI-watch → merge. Train width is yours to configure — we keep ours at one — so what lands never raced another PR's CI.

Contracts, shown

Developers believe config they can read.

Two checked-in files carry the whole process. You can keep reading by hand too; nobody will revoke your keyboard.

detent.yaml
tracker: { mode: projectv2 }
gates:
  validate: make check
  review: automated        # current-head PR review
  merge: ci_green + quiet 10m
scheduling: { parallel: 4, lease: 30m, retries: 2 }
WORKFLOW.md
1. The issue is the spec. Do not exceed it.
2. Work only in the assigned worktree and branch.
3. Run `make check` before every push.
4. Unresolved review feedback returns you to Rework.
5. Never merge. The train merges.

One host, many repos

A fleet, not a session.

Five repositories, one queue of well-specified work, no babysitting five chat sessions. Weights, priority, pause, fair scheduling — and budget caps so parallelism never surprises your bill. Detent can also log the bugs it finds, gate them like any other issue, and ship the fix — hands-off if your project config says so.

Install is a single file.

One CGO-free Go binary for macOS, Linux, and Windows. No service to stand up.

# macOS
$ brew install digitaldrywood/tap/detent
# anywhere with Go 1.26+
$ go install github.com/digitaldrywood/detent@latest
# then
$ detent doctor # preflight: gh, codex sign-in, token scope
